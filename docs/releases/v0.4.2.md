# EveryPivot v0.4.2 Release Notes

Release date: 2026-06-02

v0.4.2 is a release-readiness tooling and validator-simplification release.
It ships a new reachable-history scanner, an HTTP-probe extension to an
existing metadata check, new CI gates, a release playbook, and a
release-commit-message convention. The pattern corpus, schema, fixtures,
and release-pack composition are unchanged. The `pivot-pattern` schema
remains at v1.4. Counts remain 21 validated, 76 working_set, 79 deferred
(176 total).

## Added

- `tools/check_reachable_history.rb` (with tests and an allow-list):
  ref-scoped scanner that iterates every commit reachable from a given
  ref (default `HEAD`) and reports findings against a configurable
  pattern list. Default patterns cover AWS access keys, GitHub personal
  access tokens, OpenAI and Anthropic API keys, Slack tokens, and PEM
  and PGP private-key headers. POSIX ERE so the tool runs on macOS and
  Linux git alike.
- `--probe-live BASE_URL` extension to `tools/check_release_metadata.rb`:
  asserts the paths declared in `release-manifest.json` `site.homepage`
  and `site.patterns` actually resolve on the deployed surface. HTTP 200
  passes; 404 fails (drift between declared and deployed); 5xx and
  network errors are warnings (transient, not release defects).
  Retry-with-backoff included.
- `docs/RELEASE_PLAYBOOK.md`: names four release stages (candidate,
  release-prep, tagged-undeployed, deployed) and the per-stage
  checklist. Documents the commit-message convention and the named
  limits of each release-readiness tool.
- `docs/PROMOTION_CHECKLIST.md` gains a short section describing when a
  release commit needs a descriptive body rather than a one-line
  subject.
- New CI steps in `.github/workflows/validate.yml`: REUSE lint
  (`pipx install reuse; reuse lint`) plus the reachable-history scan
  and its test suite. The workflow now checks out with
  `fetch-depth: 0` so the history scan sees every reachable commit.

## Changed

- `tools/build_release_pack.rb` `authority_note` is simplified: stable
  and authoritative release packs now carry the generic note
  "Authoritative public registry pack." Unknown authority statuses fall
  back to a generic stringification. The longer environment-conditioned
  note strings used by non-canonical release modes have been removed
  from the public copy of the tool.
- `tools/check_release_metadata.rb`, `tools/check_site_links.rb`, and
  `tools/check_site_snapshot.rb` are simplified: they now run in a
  single mode with no dual-mode toggle. Assertions that were previously
  relaxed in one mode are now applied unconditionally.
- `tools/test_build_release_pack.rb` was trimmed to cover only
  canonical-stable behaviour. The non-canonical artifact-mode test case
  was removed from the public test suite.
- Minor doc sanitization in `docs/releases/v0.3.0.md` and
  `docs/SCHEMA_V1_5_PROPOSAL.md` to remove phrasing that implied
  operational structure outside the public repository.

## Notes

- Corpus count remains 176. Lane counts unchanged at 21 / 76 / 79.
- No `pivot-pattern` schema-version change; remains v1.4.
- No new public real-case material introduced.
- The new CI gates are additive: they fail the build only on new
  drift, not on historical accepted-risk findings recorded in
  `.reachable-history-allowlist`.
- The MANIFEST.json `provenance.note` string in any newly-built stable
  release pack now reads "Authoritative public registry pack." rather
  than the longer string carried by prior stable release packs. The
  authority_status value itself (`canonical`) is unchanged, so any
  downstream tooling parsing `authority_status` rather than `note` is
  unaffected.

## Why these tools exist

The reachable-history scanner and the live-probe extension close gaps
the v0.4.1 release review made visible. Static-only validators cannot
detect a deployed-surface mismatch on the live deploy, and working-tree
grep cannot detect an earlier commit's secret-shaped literal. The
release playbook formalises the four-stage framework so review checks
match what the artifact actually is, rather than what ship-day
expectations would otherwise impose on a release candidate.
